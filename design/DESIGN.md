# Banished Into The Abyss — Design Doc v0.1

Idle PBBG. Text/UI presentation (no game art needed). Hard player ceiling ~400. Hosted free on Netlify (frontend) + Supabase (Postgres, Auth, Realtime). Tick-based combat and guild bosses — nothing requires players to be online at the same moment.

## 1. Premise & tone

You were cast out — banished into the Abyss, a bottomless, layered pit that gets stranger and more hostile the deeper you go. There's no returning to the surface; the only way out is down. Each layer ("Depth") is harder than the last, and going deep enough to survive it at all requires periodically giving up your current strength to descend further empowered — a prestige loop that *is* the descent narrative, not just a number reset bolted onto a theme.

## 2. Core loop

1. **Idle progression.** Characters passively train/explore in the background. Progress is computed lazily: every time the client talks to the server (page load, action, periodic poll), the server calculates elapsed real time since `last_tick_at` and grants XP/gold/resources for that window, capped at a max offline duration (e.g. 24–72h) so idle gains don't become infinite AFK exploits. This avoids needing a always-on background worker — important since it's the one design choice that keeps the game fully alive on free-tier hosting (see §6). `perform_idle_tick()` (the function that runs this catch-up) also now *simulates real combat* for the elapsed window, not just passive income: it spends actions and fights the player's current pack at the same one-action-per-8-seconds cadence as online play, sharing its exact per-action combat resolution with §4b's online strike via a common `resolve_combat_action()` core, so offline kills/deaths/xp/gold and pack state come out identically to what would have happened had the tab stayed open. Capped by both the same offline-duration cap above and the player's actual action pool (an empty pool means no offline fighting, same as running dry online). This closed a real gap: before it existed, `profiles.actions` only ever ticked down while a browser tab was open and polling, so time spent offline drained nothing and fought nothing.
   **BUGFIX (post-itemization pass):** because `doTick()` in `app.js` calls `perform_idle_tick()` on *every* routine `TICK_INTERVAL_MS` poll (not only on reconnect), and `seconds_per_action` was tuned to exactly match that same 8s cadence, this catch-up combat loop was firing on essentially every single online tick too — silently fighting and killing the pack with no round-by-round log (`p_build_log=false`), then stamping `player_combat.last_strike_at`, which gated out the very next `strike_enemy()` call (the only path that ever builds an animated log for the client) as "on cooldown." Net effect: real combat kept happening every 8s, but almost always invisibly, reading as "health bars never move" and "always wins." Fixed by gating the catch-up loop's `n_actions` behind a `combat_catchup_min_seconds` threshold (20s) comfortably above one routine tick, so routine online polling leaves combat entirely to the visible `strike_enemy()` path as originally intended, and this function's own silent catch-up only fires for a genuine gap (a backgrounded/throttled tab, a closed tab, a reconnect).
2. **Active actions.** Logged-in players can spend actions/energy on: training a stat, delving into the current Depth for loot and boss-damage contributions, crafting, or trading. Implemented so far: each idle tick also auto-spends 1 action to strike the player's current solo enemy (see §4b); once actions hit 0 the auto-strike pauses gracefully (no error) until the player clicks Refresh Actions — idle XP/gold income is unaffected either way. The same action pool is now also spent by offline catch-up (point 1 above), so a full pool can be run down by either being online and idling, or simply being away.
3. **Banishment (prestige).** At level 100, a character can be Banished — sacrificed to the Abyss in exchange for +1 Depth (displayed to players as "Banishments"), carrying forward a slice of their current attack/defense/max HP sized by how many times they'd already Banished before this one (see §3 for the exact tiers). This is the "infinite slow scaling" mechanic: each life restarts small at level 1, but the compounding Banishment-count-driven retention plus the Depth-driven idle income multiplier (§7) mean a character on their 5th banishment plays entirely differently from a first-timer, without any single life's raw numbers ever needing to overflow into absurd territory. Depth ("Banishments") is a visible status symbol (leaderboards, chat name tags). (There used to be a separate Abyssal Prowess currency driving this instead of Depth directly — removed; Depth already *was* the banishment count, so routing retention through a second number that just tracked Depth 1:1 was pure indirection.)
4. **Endgame.** The exciting part isn't "the biggest number" — it's what unlocks at Depth/Banishment milestones: new guild-boss tiers, cosmetic chat titles/tags, rare crafting recipes, and eventually **Abyssal Rifts** — timed, high-difficulty solo or guild content that only very deep characters can enter, with unique rewards that feed back into guild bosses (see §5). Endgame players are never "done"; they're gated by Depth-gated content, not by a stat treadmill.

## 3. Characters & economy

- One character per account (simplifies balance and abuse surface for a 400-player game).
- One currency: **Gold** — everyday, earned constantly, spent on gear/consumables. (There used to be a second currency, Abyssal Prowess, earned only by Banishing; it's been removed — see the Banishment retention tiers below, which now read directly off Depth instead.)
- **Death penalty** (implemented in `strike_enemy()`): currently 0% gold and 0% xp lost on death — no economic cost to dying at all. This used to be 25%/10%, back when it was the counterweight to how freely Number of Enemies Spawned / Number of Affixes / Player Debuffs could be pushed (those knobs have no ceiling and reward proportionally harder fights, so without a real cost for losing there'd be no reason not to max every one of them and grind through deaths for free). It was zeroed out deliberately once automatic Banishment-depth scaling (see §2.3/`enemy_effective_stats()`) started covering that same "don't overreach for free" role on its own — every fight gets harder forever regardless of what the player picks, so losing already has a natural ceiling without also needing an economic tax. The mechanism (win-only rewards, a full heal, a tracked 'death' event) is untouched — only the two percentages moved to 0. TUNE back up if playtesting says 0 feels too safe.
- **Banishment retention tiers** (implemented in `perform_banishment()`, gated to level 100+): the tier is set by how many times the character has *already* Banished (`profiles.depth`, displayed as "Banishments") before this banishment.

  | Banishments already reached | % of (attack / defense / max HP above base) retained |
  |---|---|
  | 0 – 9 | 0.25% |
  | 10 – 49 | 0.50% |
  | 50 – 99 | 0.75% |
  | 100+ | 100% (full retention) |

  (These are a straight /10 rescale of the old Abyssal-Prowess tiers — 100/501/1001 — since Prowess was always earned at a flat `floor(level/10)` = 10 per banishment given the level-100 minimum, so it tracked Depth 1:1. Same pacing/milestones as before, just one fewer currency to track.)

  Each banishment grants +1 Depth; level/xp/gold reset to 1/0/0, inventory, equipped/unequipped gear, and the current solo fight are all cleared, and HP/actions come back full. Gear is wiped for the same reason inventory always has been: a Banishment reset that left gear untouched would make itemization a second, ungoverned retention channel running alongside the real one (stat retention above). All constants are marked `-- TUNE` in `schema.sql` — first-pass numbers, not balanced yet.

  **Level-scaled stat growth** (`level_stats()` in `schema.sql`, added post-v0.008): attack/defense/max HP used to sit completely flat at the signup default for a character's *entire* first life — level was purely a display/xp-threshold number with zero effect on combat power, so the level 1-100 climb was mechanically identical throughout. `level_stats(level)` fixes this with a linear 1-to-100 growth curve, applied by `perform_idle_tick()` as an additive delta on level-up (never an absolute overwrite, so it composes correctly with whatever a prior Banishment already retained instead of erasing it):

  | Level | Attack | Defense | Max HP |
  |---|---|---|---|
  | 1 (signup default) | 8 | 6 | 30 |
  | 50 | 14 | 10 | 52 |
  | 100 | 20 | 15 | 75 |

  Level 1 is anchored to `profiles`' actual signup default (8/6/30); level 100 (20/15/75, a flat 2.5x across all three stats) is what `perform_banishment()` now reads as its "base" retention floor too, instead of a separately hardcoded copy that could drift out of sync. That fixes a second, previously-unnoticed problem: the old hardcoded floor was *also* just the signup default, so a first-time banisher — whose stats, with no per-level growth existing yet, had never moved off that same default — retained a percentage of exactly zero above base. Banishment changed Depth only, not combat power, for anyone banishing for the first time. Now that level_stats(100) sits meaningfully above the signup floor, reaching level 100 before banishing actually matters.

  **Important, and still true now that itemization exists (see §3b):** the attack/defense/max HP that retention reads are `profiles`' own base columns — a character's *own* permanent growth, via leveling (`level_stats()` above) and Banishment retention itself, untouched by anything else. Gear **never** mutates these columns directly. Gear stats apply the same way `class_defs`' class bonuses already do — a separate, combat-time-only modifier bundle (see `resolve_combat_action()`'s `player_mods`/`p_gear_mods` in `schema.sql`), invisible to `perform_banishment()`. If gear were instead baked into `profiles.attack/defense/max_hp`, equipping strong gear right before banishing would let a player permanently bank power they never actually earned on the character itself — gear stays swappable/losable (and is wiped outright on Banishment, see above), never something Banishment can launder into permanent retention.
- Items live in a simple `items` catalog (key, name, rarity, type) with per-player `inventory` rows. Text-only presentation means items just need good names/flavor text, no art pipeline. This is separate from equippable gear — see §3b.

## 3a. Stats

All six standard stats are wired into `resolve_combat_action()` in `schema.sql` — Speed was the last one, added along with pack combat's initiative/evasion mechanics (see below).

**Standard stats** (every character has these; leveling and standard-slot gear raise them):
- Power
- Defense
- Attack Speed
- Crit
- Multi Strike
- Speed — decides which side (player or the current pack) swings first each round, compared against the pack's average Speed among currently-alive members and recomputed every round (ties go to the player); also grants **Evasion**, a flat chance to dodge an enemy hit entirely, at 1 Speed = 1% Evasion, hard-capped at 50%. Both are implemented directly in `resolve_combat_action()`/`pack_counterattack()`, not via the general `compute_damage()` modifier vocabulary, the same way Multi Strike and Attack Speed already weren't — see `evasion_flat`/`speed_pct` in the class-bonus comment there for how a class bonus, gear roll, or affix can add to either.

**Special stats** (relic-only — never trained, only found rolled on Relic-slot gear, see §3b):

| Stat | Rate | Cap | Effect |
|---|---|---|---|
| Dodge | 1% per roll | 25% | Fully dodges an attack |
| Block | 1% per roll | 25% | Halves incoming damage |
| Parry | 1% per roll | 25% | Deflects 25% of the incoming damage |
| Riposte | 1% per roll | 25% | Returns 25% of the incoming damage |
| Abyssal Touch | flat, 3 per roll | none | Adds abyssal damage |
| Thorns | flat, 5 per roll | none | Deals flat thorns damage back on being hit |
| Bristle Back | up to 5% per roll | none | Multiplier on Thorns damage |
| Life Steal | 1% per roll | 50% | Heals the player for a % of damage dealt |
| Bleed | 1% per roll | 25% | Target bleeds for a % of damage over time |
| Increased XP | 2% per roll | none | Multiplier on all XP gained — combat kills and the passive idle trickle alike |
| Increased Item Find | 3% per roll | none | Multiplier on the per-kill loot drop roll (§3b) — does not change the stored 15% base rate, only the effective chance |

Note the overlap with Speed's core-stat Evasion above: relic-only Dodge (1%/roll, cap 25%) is a separate, additive source of the same "fully avoid this hit" outcome, not a duplicate to reconcile away — a character can eventually stack Speed-derived Evasion and relic-rolled Dodge on top of each other. Whether they should share one roll-check or stay two separate ones is still a TUNE decision.

**Status: all eleven of these stats can be rolled, equipped, AND are now live in combat math.** The nine that used to sit inert (Dodge, Block, Parry, Riposte, Abyssal Touch, Thorns, Bristle Back, Life Steal, Bleed) were wired up in a follow-up pass, same "staged then implemented" arc Speed/Evasion itself went through earlier. Two different mechanical treatments, matching how each stat reads in the table above:

- **Chance-gated procs** (Dodge, Block, Parry, Riposte): the stat's own value directly IS a per-hit percentage chance, same convention `crit_chance_flat`/`multi_strike_flat` already use elsewhere — not "chance to gain more of the stat," the stat *is* the chance. All four are independent rolls inside `pack_counterattack()`, so more than one can matter on the same incoming hit: Dodge and Evasion are each rolled separately (see the note above about them stacking as two sources of the same outcome — Evasion first, then Dodge if Evasion didn't already avoid it), then, if the hit wasn't avoided, Block and Parry are each rolled independently and stack multiplicatively when both land (halved, then cut by another 25%), then Riposte is rolled against the final post-mitigation damage.
- **Deterministic per-hit magnitudes** (Life Steal, Bleed) and **always-on flat bonuses** (Abyssal Touch, Thorns, with Bristle Back as a pure multiplier on Thorns): no roll at all — every landed hit applies them, scaled by the stat's own (capped) value. Life Steal heals the player for a % of that hit's damage; Bleed applies (refreshing, not stacking) a DoT on the target worth a % of that hit's damage, ticking once per round for 3 rounds (`bleed_duration_rounds`, TUNE) via a new `apply_bleed_ticks()` helper called at the top of every round in `resolve_combat_action()`'s loop, before initiative — a kill from Bleed is caught by the same `any_alive` check that already handles every other kill, not a special case. Abyssal Touch adds its flat value to every player hit (after `compute_damage()`'s own crit/mitigation math, so it's a flat add, not itself crit-inflated); Thorns reflects a flat amount back at whichever pack member just hit the player (scaled by Bristle Back), whether or not that hit was Blocked/Parried down to a smaller number — only full avoidance (Evasion/Dodge) skips Thorns/Riposte entirely.

Thorns and Riposte reflect damage back onto the SPECIFIC attacking pack member, not a random one, which is why `pack_counterattack()` now returns the (possibly modified) pack alongside its hp-delta and hit log, not just the delta — a design also required so a kill from reflect damage is visible to the rest of the fight immediately rather than needing its own bookkeeping. All of this reflect/DoT/heal damage folds into the same `damage_dealt`/`cur_player_hp` totals every other source already did, so nothing downstream (the client, `strike_enemy()`, `perform_idle_tick()`) needed to change — `combat_action_result`'s shape is unchanged by this pass.

The Combat Stats panel's **Additional Affixes** section (client-side, `renderAdditionalAffixes()` in `app.js`) sums these eleven keys across whatever's currently equipped and shows only the ones with a nonzero total, capped for display the same way the server caps each one for real (with a tooltip flagging it when a player has rolled more than the cap can use) — it used to be four permanently-empty placeholder rows with no logic behind them at all.

The other two — Increased XP (`xp_gain_pct`) and Increased Item Find (`item_find_pct`) — are the exception and are fully live: `xp_gain_pct` is read via `mod_val()` in `resolve_combat_action()`'s pack-clear XP award and in `perform_idle_tick()`'s passive trickle formula; `item_find_pct` is read in the drop-roll check both functions run per kill. They were shipped functional from the start since they're plain economy multipliers with no new combat subsystem to design, unlike the nine above.

## 3b. Itemization: gear, rarity, and drops

Gear is a separate system from the `items`/`inventory` materials catalog in §3 — every piece of gear is procedurally rolled per drop (its own row, its own specific stats), not a shared catalog + quantity, since no two drops of "the same" weapon actually roll the same. Implemented in `schema.sql`: the `equipment` table, `roll_loot()` (the procedural generator), `equip_item()`/`unequip_item()` (the only two ways a piece of gear's equipped state changes), and the drop hook inside `resolve_combat_action()`.

**Slots.** Seven physical equip slots: Helm, Weapon, Garb, Ring ×2, Relic ×2. Ring and Relic share one slot *type* each server-side (`equipment.slot` is `'ring'`/`'relic'`, not per-box) — `equip_item()` only enforces "at most 2 of this type equipped," not which of the two UI boxes either one renders in, since both rings'/relics' mods sum into combat identically regardless.

**Rarity and drop rates.** Seven tiers, White → Orange the player specified, plus two chase tiers above Legendary:

| Rarity | Odds | Roughly |
|---|---|---|
| Junk (white) | 45% | almost half of all drops |
| Common (green) | 30% | |
| Rare (blue) | 15% | |
| Epic (purple) | 7% | |
| Legendary (orange) | 2.4% | ~1-in-42 |
| Void Touched | 0.5% | ~1-in-200 |
| Void Spiraled | 0.1% | ~1-in-1000, the ultimate chase item |

A clean 100% split. White+Green alone cover 75% of drops (routine vendor filler — Junk always rolls with zero stat mods), each tier up roughly halves or better, and the two Void tiers sit meaningfully further out than a normal Legendary since they're meant to be long-run chase items, not just "the best normal roll." All of it lives in `roll_loot()`'s `rarity_weights` array — a `-- TUNE` constant like everything else.

**Drop trigger.** Rolled once per "kill" (a full pack clear — the same event that already grants xp/gold, not per individual pack member) at a flat ~15% chance, so most clears grant nothing, some grant one item. Not scaled by pack size, same simplification `reward_mult` already leans on for xp/gold. Fires from both `strike_enemy()` (online play) and `perform_idle_tick()`'s offline-combat loop (so a long catch-up can return having found several items at once — the client's Welcome Back summary surfaces an Items Found count when that happens).

**Stat rolls by slot.** Helm/Weapon/Garb/Ring roll from the six standard stats (§3a) — each roll picks a *distinct* key at a magnitude scaled by rarity (roughly +2..5 at Common up to +30..45 at Void Spiraled). Relic rolls from the eleven relic-only stats (§3a) using their own "N per roll" convention instead — each roll adds a small fixed amount to a *randomly chosen* relic key, so a high-rarity Relic can stack the same stat multiple times rather than always spreading across distinct ones. Number of rolls scales with rarity: Junk 0, Common 1, Rare 2, Epic 3, Legendary/Void Touched 4, Void Spiraled 5.

**Naming.** Fully procedural, no fixed item catalog: a rarity-flavored adjective (Crude/(none)/Sturdy/Exquisite/Mythic/Voidtouched/Void-Spiraled) + a slot-appropriate void-themed base name + an "of `<Stat>`" suffix drawn from one of the item's own rolled stats. No unique named items yet — that's a natural future pass once the base system has been played with.

**Equipping.** `equip_item(p_equipment_id, p_unequip_id default null)` enforces the slot caps (1 Helm/Weapon/Garb, 2 Ring, 2 Relic) — a full slot raises an exception asking for a specific item to swap out (`p_unequip_id`) rather than silently auto-unequipping something on the player's behalf. Both RPCs return the caller's whole `equipment` set so the client can refresh in one round trip.

The client never surfaces that "slot is already full" exception to the player as an error, though — `equipItem()` in `app.js` catches it and resolves `p_unequip_id` itself, then retries: for Helm/Weapon/Garb there's only one item that could possibly be occupying the slot, so it just swaps it in with no prompt. Equipping a bag item onto a full slot is a plain swap from the player's perspective — click Equip, done.

For Ring/Relic, where two pieces could be equipped, WHICH one gets replaced is a left-click-vs-right-click on the bag item's Equip button: left-click targets equip-slot box 1 (`eq-slot-ring-0`/`eq-slot-relic-0`, labeled "Ring 1"/"Relic 1" in the Equipment panel), right-click (`contextmenu`, suppressed from opening the browser's own context menu) targets box 2. This only matters when both boxes are already full; with an open slot, `equip_item()` fills it directly and the click side is never consulted. The two-`confirm()`-dialog chooser (`chooseReplacementId()`) that used to be the only way to disambiguate this is kept as a fallback for a call with no left/right-click info behind it, but the button itself no longer uses it.

**BUGFIX (right after this shipped): box 1/box 2 needed to be a sticky, explicit assignment, not a re-sort.** The first version had `renderEquipmentSlots()` deciding "box 1 vs box 2" by filtering `state.equipment` down to that slot's equipped rows and reading index 0/1 straight off the array — ordered by the query's `created_at DESC` (drop time), which has nothing to do with which physical box a swap should land in. A right-click meant to replace box 2 WOULD correctly unequip whatever box 2 held server-side, but the newly-equipped item's own `created_at` could sort it right back into box 1 on the next render, making the swap look like it landed in the wrong slot. Fixed with `state.equipBoxAssignment` (`{ ring: [id|null, id|null], relic: [id|null, id|null] }`) as the actual source of truth for which id is in which box, mutated explicitly in exactly two places: `reconcileEquipBoxAssignment()` (called at the top of every `renderEquipmentSlots()`) clears a box whose id got unequipped and fills any now-empty box with an equipped id nothing else claims yet — this is the ONLY path that assigns by array order, and only for ids with no prior assignment (a fresh signup's first two rings, say); and `equipItem()`'s own success path, which — whenever a swap just happened (`unequipId` was set) — looks up whichever box was tracking the unequipped id and hands that exact box to the newly-equipped item instead, so the swap visibly lands where the player clicked. The left/right-click resolution itself (in `equipItem()`'s "already full" branch) reads `preferredSlotIndex` against this same `state.equipBoxAssignment`, not a fresh filter, so what the player sees and what the click resolves to can no longer disagree.

**What actually affects combat today:** Helm/Weapon/Garb/Ring gear's standard-stat mods are merged into `player_mods` in `resolve_combat_action()` (via a `p_gear_mods` parameter both `strike_enemy()` and `perform_idle_tick()` populate from the equipped rows before calling it) — equipping a +Power weapon measurably changes damage output immediately. Relic gear's mods merge in too, but — per §3a above — nothing reads those specific keys yet, so equipping a Relic today changes nothing about a fight until the follow-up mechanics pass lands.

**Item level.** Every drop is tagged with `equipment.level` — the character's level at the moment it dropped, set from `p.level` right where `resolve_combat_action()` builds the drop's jsonb entry. Purely informational (shown on the item's popup, see below) — never itself a power lever, since combat only ever reads a piece of gear's `mods`.

**The bag: cap, sub-headers, and scrapping.** Unequipped gear renders inside the same Inventory panel as the materials/trinkets catalog (§3), not a separate Gear panel — grouped into per-slot-type sub-headers (Helm, Weapon, Garb, Ring, Relic, each only shown when it has at least one entry), sorted in that fixed order rather than alphabetically or by drop time. The bag is capped: 250 unequipped gear pieces is the number shown to the player ("Bag: X / 250"), with a quiet +10 grace past that before anything is actually turned away, so a player is never cut off exactly at the advertised number with zero warning. Once the true hard cap (260) is hit, any further drop is auto-scrapped instead of silently discarded — a kill's reward should never just vanish for nothing. All of this is enforced server-side in `persist_loot_drops()`, shared by `strike_enemy()` and `perform_idle_tick()` so it behaves identically online and during offline catch-up.

Every scrap path — this cap overflow, the player's own standing rarity settings below, a manual single-item scrap, or a bulk bag cleanup — destroys the item for a flat, rarity-based gold value (`scrap_value()`, a `-- TUNE` schedule roughly doubling per tier, same shape as the rarity odds themselves).

**Auto-Scrap and Clean Bag.** `profiles.auto_scrap_rarities` is the player's own standing "always convert this rarity to gold the instant it drops" list, set via `set_auto_scrap_rarities()` and checked right inside `resolve_combat_action()`'s drop-roll branch — a matching rarity never even touches `loot_drops`/the bag, it's converted straight to gold. Empty by default (opt-in, never silently scrapping a first-time player's early Junk without them choosing to). `cleanup_bag()` — the Inventory panel's "Clean Bag" button — applies that same list retroactively, in one batch sweep, to whatever's already sitting in the bag right now, so turning on a rarity doesn't mean waiting for it to naturally cycle out. Manual, single-item scrapping (`scrap_equipment()`, a "Scrap" button on each bag row) is the primitive both of the above ultimately reduce to.

**Item popup.** Hovering (desktop) or tapping (mobile — there's no hover, so a first tap previews and, on an equip-slot box, a second tap confirms the unequip) any equip-slot box or bag row shows a small popup with the item's full name, rarity, slot, level, and complete stat list. One shared popup element, positioned near whatever triggered it — see `showItemPopup()`/`attachItemPopup()` in `app.js`.

A bag row's popup additionally shows a "vs equipped" comparison against whatever's currently equipped in that same slot: one stat-delta line per stat that differs (green for a gain, red for a loss), covering stats the candidate item lacks but the equipped one has (shown as a loss) and vice versa, not just stats both share. Ring and Relic each have two equip slots, so a bag ring/relic compares against both equipped pieces separately, each under its own "vs `<name>`" heading; Helm/Weapon/Garb (one slot) just get a single "vs equipped" block. If nothing's equipped in that slot yet, the popup says so instead of showing a diff. An equip-slot box's own popup never shows this section — comparing an equipped item to itself is meaningless. See `buildComparisonSection()`/`computeStatDiffLines()` in `app.js`.

## 4. Guilds & guild bosses

- Guilds: name + tag, leader/officer/member roles, guild chat channel, member cap (recommend 20–30 given the 400-player ceiling — enough for ~15-20 guilds to exist).
- **Guild bosses**: each guild has a rotating boss with a shared HP pool. Members contribute damage passively (a slice of their idle-tick output is auto-applied to the active boss) — implemented as the sole damage source now; a manual strike button was removed in favor of pure idle-tick feeding. All damage is server-validated (see §6) so nobody can fabricate a hit.
- Defeating a boss distributes loot weighted by each member's contribution share, logs a "last hit" and "top damage" callout in guild chat, and starts a cooldown before the next (harder) boss spawns. Boss tier scales with the guild's average Depth, so a guild of shallow characters and a guild of deep ones both have a boss that's meaningfully hard for them — this is what keeps guild bosses relevant forever instead of being trivialized once players outscale them.
- Because boss HP/respawn state is just rows with timestamps, it's evaluated lazily on read exactly like idle ticks — no cron required to keep a boss "alive."

## 4b. Solo combat (one continuous fight, no zones)

A standalone player-vs-mob loop (`enemies`, `player_combat`, `strike_enemy()`) drives the "Current Battle" panel independently of guild bosses. There is deliberately no zone/dungeon-select screen and never will be one: it's a single ongoing encounter that scales forever (see the Banishment depth-scaling in `enemy_effective_stats()`) and pulls from a growing mob roster instead of gating progress behind discrete areas the player has to leave and re-enter. Each idle tick auto-strikes the current pack (1 action per strike); a kill or a death respawns a fresh pack immediately, so there's always a fight in progress.

The one-action-worth-of-fighting logic (initiative, swings, Multi Strike, kill heal, pack-clear/death handling, affix/debuff reroll on respawn) lives in a shared core, `resolve_combat_action()`, rather than inside `strike_enemy()` itself. `strike_enemy()` is now a thin wrapper around it (one DB read, one call, one DB write) used while the player is online; `perform_idle_tick()` (§2.1) calls the same core in a tight in-memory loop to simulate whatever fighting would have happened while the player was offline, so the two paths can never drift apart in behavior.

**Same-window clear bonus / timeout refresh (v0.018).** `resolve_combat_action()` only ever fights ONE pack per call, inside a bounded round loop (`rounds_soft_budget`, attack-speed-scaled off `base_rounds`; `rounds_hard_cap` as an absolute ceiling) — the "tick window" for that pack, equally whether the call came from an online `strike_enemy()` press or one iteration of `perform_idle_tick()`'s offline catch-up loop. What happens when that window ends now depends on whether the pack's fate was actually decided within it: a new `pack_outcome_resolved` flag starts false and is set true the instant the pack clears or the player dies against it (both existing respawn points). If the round budget runs out with the pack still neither cleared nor lost — i.e. the player selected more pack size/affixes/debuffs (Encounter Settings) than could be finished in one window — the pack is discarded and replaced with a freshly-rolled one, granting no xp/gold and, deliberately, no heal (a timeout isn't a death, so `cur_player_hp` is left exactly where the window ended it — otherwise overshooting pack size for free heals would be an exploit). This replaces the old behavior of quietly carrying a partially-damaged pack into a later call to keep chipping away at it. The flip side: because an unresolved pack can no longer reach the pack-cleared branch at all, EVERY clear that does land there is now guaranteed to be a full clear of the player's entire chosen pack within a single window — so that branch's XP award is unconditionally doubled (`pack_xp * reward_mult * (1 + xp_gain_pct/100) * 2`) with no extra check needed. Gold is deliberately left out of the doubling — this was requested as an XP bonus specifically, not a gold one. Verified locally against hand-built packs sized to force each outcome: a pack too tough to clear within `rounds_soft_budget` came back as a full-HP fresh pack with `rounds_run == rounds_soft_budget`, zero xp/gold, and player HP unchanged (not reset to max); an easily-cleared pack returned exactly double the pre-change xp formula's value with gold unaffected; and the existing death-respawn path (full heal to max HP) was confirmed unaffected by the new flag.

The `enemies` table holds the mob roster — as of v0.008, 100 void-themed mobs (Void Mote, Rift Crawler, Hollow Leech, Umbral Shade, Hollow Colossus, and so on, spread across a handful of flavor archetypes: swarm motes, vermin, fast skitterlings, bruiser leeches/oozes, flyers, hounds, tanky grubs, balanced husks, wraiths, and a higher-ceiling "void-touched" tier), each just a set of base stats/flavor. `roll_pack()` picks a random eligible enemy **per pack member**, not once for the whole pack, so a single fight can mix species rather than always being a uniform pack of one kind. Eligibility is gated by `enemies.min_depth` (the player's current Banishment count) — this is a pure variety/content gate, deciding which mobs *can* show up, never a power gate; all real difficulty still comes from the existing tier/depth/variance multiplier in `enemy_effective_stats()`, applied uniformly no matter which mob got picked. All 100 currently sit at `min_depth` 0 deliberately, so the whole roster can roll at any point across the level 1-100 journey rather than being gated behind Banishment count — depth stays 0 for a character's entire first life, so anything gated higher wouldn't be seen until well past a first Banishment. The column stays in place as infrastructure for a future post-Banishment content pass (new mobs unlocking per Depth), it just isn't used that way for this roster. Elite/champion spawns (`roll_enemy_tier()`, 10%/5% odds, 1.25x/1.5x stat multiplier) apply uniformly to whichever mob got picked, same as always.

Adding more mobs later is just adding rows — no combat-loop changes needed, same as an affix or debuff.

## 5. Social systems

- **Global chat** — one shared channel, Supabase Realtime broadcast, rate-limited server-side (e.g. 1 message / 2s per user) to keep it usable at up to a few hundred concurrent chatters.
- **Guild chat** — same mechanism, scoped to guild members only via RLS.
- **Whispers (`/w name message`)** — private 1:1 messages, delivered over the same Realtime channel the recipient is already subscribed to (their own user-id channel), so no polling needed.
- **`/send name item|gold amount`** — transfers items or gold between two players. This is the highest-abuse-risk feature in a small free game (multi-accounting, scam funneling), so it never touches the table directly from the client: it goes through a single server-side function that checks balance, logs every transfer (sender, recipient, what, when) to an immutable `item_transfers` table, and enforces a small per-transfer and per-day cap plus a short cooldown. That log is also what makes it possible to investigate a dispute after the fact.
- Both chat and `/send` are implemented as slash commands parsed client-side and dispatched to the same small set of server functions — no separate "trade UI" needed for v0.

## 6. Why this stays free at ~400 players

- **Netlify Free**: 300 credits/month (deploys ≈15 credits each, bandwidth ≈20 credits/GB, ~10k requests ≈2 credits). A static text-UI frontend for a few hundred users comfortably fits; the main thing to watch is bandwidth if chat volume gets heavy, which is a reason to keep payloads small (plain JSON, no big assets).
- **Supabase Free**: 500MB database, 1GB file storage, 50,000 monthly active users, 5GB egress, 500,000 Edge Function invocations, and — the one that matters most here — **200 concurrent Realtime connections**. At a 400-player *cap*, not every player is online simultaneously, but if the game ever gets popular enough to regularly have 200+ concurrent browser tabs open, that's the first free-tier wall you'll hit — and the natural place to start paying (Supabase Pro), not a reason to avoid this stack now.
- **The one real gotcha**: Supabase free projects **pause after 7 days with no activity**. A cron-driven world (bosses ticking down on a timer even with nobody around) would silently stop. That's exactly why §2 and §4 use lazy, read-time computation instead of a background scheduler — the game state only needs to be *correct whenever someone next looks*, not continuously animated in the background. As a belt-and-suspenders measure, a free external pinger (e.g. a GitHub Actions cron hitting a health-check endpoint weekly) keeps the project from ever pausing at all.

## 7. Data model (implemented in `supabase/schema.sql`)

`profiles`, `guilds`, `guild_members`, `guild_bosses`, `guild_boss_damage_log`, `items`, `inventory`, `enemies`, `player_combat`, `banishments`, `chat_messages`, `whispers`, `item_transfers`. Mutating actions (idle tick resolution, boss attacks, solo strikes, banishment, sends, chat/whisper posts) go through `SECURITY DEFINER` Postgres functions rather than raw table writes, so all game rules are enforced in one place regardless of client.

## 8. Open design questions for later passes

- Exact XP/gold curve constants, Depth thresholds, and Banishment tier/gain numbers (needs a balancing pass once there's something playable to test against).
- The full stat system in §3a needs an itemization/relic layer designed before it can replace the current placeholder attack/defense combat math — and per §3, that layer must be a `player_mods`-style modifier bundle, never a write to `profiles`' base stat columns, so Banishment retention can never accidentally bank gear power.
- Whether guilds need a shared bank in addition to `/send`.
- PvP: not in scope for v0 — flagged here so it's a deliberate future decision, not an oversight.
- Moderation: with live chat at this scale, a lightweight mute/ban table and a couple of admin-only RPCs are worth adding before public launch.
